# 서울 지하철 1호선·2호선 노선 구조 메모 (DB 점검용)

작성 기준: 2026-03-18 확인 자료 기준

## 이 문서의 목적

DB 구조를 점검할 때, **"호선 + 상행/하행"만으로는 충분한지**를 보기 위한 메모다.
특히 2호선의 **순환 구조 + 지선**, 1호선의 **트렁크 구간 + 다중 분기/다중 종착 패턴**이 핵심이다.

---

# 1. 2호선

## 1-1. 2호선의 본질: 일반적인 상행/하행선이 아니라 순환선

2호선 본선은 **시청~시청 순환 구조**다. 그래서 일반적인 의미의 `up/down`(상행/하행)보다,
실제 승객 안내와 운행 표시는 **내선순환 / 외선순환**이 더 중요하다.

- 내선순환: 순환 본선의 한 방향
- 외선순환: 순환 본선의 반대 방향

즉 2호선 본선은 DB에서 단순히 `direction = up/down`으로 저장하기보다,
**`service_direction = inner/outer`** 같은 식으로 별도 표현하는 편이 자연스럽다.

## 1-2. 2호선은 본선만 있는 것이 아니라 지선이 따로 존재

2호선은 공식 노선 구조상 아래 3개 축으로 보는 것이 실무적으로 유용하다.

1. **본선 순환부**: 시청~시청
2. **성수지선**: 성수~신설동
3. **신정지선**: 신도림~까치산

실시간 운행 정보에서도 실제 열차 행선지가 다음처럼 표시된다.

- **내선순환**
- **외선순환**
- **신설동행**
- **까치산행**

즉 2호선은 DB에서 최소한 아래 둘을 분리해서 다뤄야 한다.

- **line = 2호선**
- **service_pattern / branch / destination**

예를 들면:

- 2호선 본선 내선순환 열차
- 2호선 본선 외선순환 열차
- 2호선 성수지선 신설동행 열차
- 2호선 신정지선 까치산행 열차

## 1-3. 2호선 DB 설계에서 특히 중요한 점

### A. `상행/하행` 컬럼만으로는 부족

2호선 본선은 순환선이므로 `상행/하행`보다 `내선/외선`이 핵심이다.
지선까지 포함하면 더더욱 `상행/하행`만으로는 의미가 약하다.

### B. `branch_key` 또는 `service_group`가 필요

최소한 아래 정도는 구분되는 편이 좋다.

- `main_loop_inner`
- `main_loop_outer`
- `seongsu_branch`
- `sinjeong_branch`

### C. `destination_station`이 중요

2호선은 실제 안내가 `신설동행`, `까치산행`, `내선순환` 식으로 노출되므로,
경로 안내/표시 레이어에서는 `direction`보다 **행선지/운행패턴**이 더 중요하다.

### D. 성수역·신도림역은 분기 거점으로 봐야 함

- **성수역**: 본선 ↔ 성수지선 분기
- **신도림역**: 본선 ↔ 신정지선 분기

따라서 line_stations 수준에서 단일 선형 순서만 가정하면,
2호선은 예외 처리가 아니라 **애초에 그래프/분기 구조**로 다뤄야 편하다.

## 1-4. 2호선에 대한 DB 결론

2호선은 다음 전제를 두고 설계하는 것이 안전하다.

- `line_id = 2` 하나만으로는 부족
- `branch` 또는 `service_pattern`이 필요
- 본선은 `up/down`이 아니라 `inner/outer`가 자연스러움
- 지선은 `신설동행`, `까치산행`처럼 **종착 기반 패턴**으로 표시하는 편이 실사용에 맞음

# 2. 1호선

## 2-1. 1호선의 본질: 한 줄처럼 보이지만 실제로는 "공통구간 + 여러 갈래" 구조

1호선은 2호선처럼 순환선은 아니지만,
DB 관점에서는 오히려 더 까다롭다.

이유는 1호선이 단순한 하나의 직선 노선이 아니라,
**도심 공통구간을 공유한 뒤 여러 외곽 방향으로 갈라지는 운행 계통**이기 때문이다.

공식 자료 기준으로 1호선은 서울 지하 구간만 따로 떼서 보기보다,
수도권 광역 1호선 전체 계통으로 이해해야 한다.

대표적으로 남쪽/서쪽 방면 종착 계통에는 아래가 포함된다.

- **인천방면**
- **신창방면**
- (열차 패턴상 자주 보이는 하위 종착) **광명행**, **서동탄행**, **천안행**, **동인천행** 등

북쪽 방면은 공식 지연증명서 기준으로 **소요산방면**으로 묶여 안내된다.

즉 1호선은 이용자 입장에서 이미 **상행/하행만으로 안내되지 않고, 방면/행선지 기반**으로 안내되는 노선이다.

## 2-2. 신도림 "쯤"이 아니라 구조적으로는 구로에서 큰 분기가 드러남

질문에서 말한 느낌은 맞지만,
DB 관점에서는 **신도림 인근에서 체감되더라도 구조적으로 중요한 분기점은 구로**라고 보는 편이 맞다.

핵심은 다음과 같다.

- 도심 공통구간을 지나 서남권으로 내려온 뒤
- **구로 이후 열차가 크게 경인선 계통(인천 쪽)과 경부선 계통(수원·병점·천안·신창 쪽)으로 갈라진다**

그래서 승객 입장에서는 비슷한 "하행"이라도 실제 서비스 패턴은 서로 다르다.

예:

- 인천/동인천 방면
- 수원/병점/서동탄 방면
- 천안/신창 방면
- 광명 셔틀 계통

즉 1호선은 **상행 하나 + 하행 하나**라고 단순화하면 DB가 금방 막힌다.

## 2-3. "상행선은 하나"라고 느껴지는 이유와, DB에서는 왜 그걸 그대로 쓰면 안 되는지

도심 공통구간에서는 체감상 북쪽 방향이 하나처럼 보일 수 있다.
하지만 실제 1호선 전체 계통은 북쪽/남쪽 모두 다양한 종착 패턴이 존재한다.

특히 DB에서 중요한 것은 **방향 그 자체보다도 어느 분기 계통을 타는 열차인지**다.

예를 들어 같은 하행이라도:

- 어떤 열차는 인천행
- 어떤 열차는 서동탄행
- 어떤 열차는 광명행
- 어떤 열차는 신창행

이렇게 달라질 수 있다.

따라서 1호선은 `direction = up/down`만 두는 구조보다,
최소한 아래 정보가 함께 있어야 한다.

- `service_direction` (northbound/southbound 정도의 큰 방향)
- `destination_station`
- `branch_key` 또는 `service_pattern`

## 2-4. 1호선 DB 설계에서 특히 중요한 점

### A. `direction`만으로 경로를 재구성하기 어렵다

1호선은 같은 방향 안에서도 종착지와 분기 계통이 다르다.
따라서 승객 안내나 경로 복원에서는 `direction`보다 `destination`이 훨씬 중요하다.

### B. 공통구간과 분기구간을 함께 표현해야 한다

예를 들면 이런 구조가 필요하다.

- **도심 공통구간**: 서울역/시청/종로/동대문/청량리 방면으로 이어지는 축
- **서남 분기구간**: 구로 이후
  - 경인선 계통(인천/동인천)
  - 경부선 계통(수원/병점/서동탄/천안/신창)
- **별도 분기 계통**: 금천구청~광명

즉 line_stations를 한 줄 순서만으로 저장하면,
1호선 역시 2호선과 마찬가지로 분기 처리에서 한계가 생긴다.

### C. `terminal-driven UI`가 자연스럽다

실제 이용자 안내는 보통 아래처럼 종착 기반이다.

- 인천행
- 신창행
- 서동탄행
- 광명행
- 소요산방면

따라서 앱/UI나 API 응답에서도 1호선은 `상행/하행`보다 **행선지 문자열**이 훨씬 유용하다.

### D. 1호선은 "노선"과 "운행계통"을 분리해서 생각하는 편이 좋다

같은 `1호선`이어도 실제 서비스는 여러 운행계통이 섞여 있다.
그러므로 DB에서 아래를 분리하는 것이 좋다.

- `physical_line` 또는 `line_id` = 1호선
- `service_pattern` = 인천계통 / 신창계통 / 광명계통 / 서동탄계통 / 북행계통 등

## 2-5. 1호선에 대한 DB 결론

1호선은 2호선과 달리 순환선은 아니지만,
**분기와 종착 패턴이 많아서 `상행/하행` 단순 모델로는 부족하다**.

실무적으로는 다음처럼 보는 것이 안전하다.

- 큰 방향: 북행 / 남행(또는 상행 / 하행)
- 실제 안내: **종착역 기반**
- 경로 계산: **분기 그래프 기반**
- 서비스 식별: **branch/service_pattern 필요**

# 3. 1호선 vs 2호선: DB 관점 비교

## 3-1. 2호선

문제의 핵심은 **순환 + 지선**이다.

필요한 개념:

- `inner/outer`
- `branch`
- `destination`

## 3-2. 1호선

문제의 핵심은 **공통구간 + 다중 분기 + 다중 종착**이다.

필요한 개념:

- `up/down` 또는 `northbound/southbound`
- `branch`
- `destination`
- `service_pattern`

## 3-3. 공통 결론

1호선과 2호선 모두 **"호선 + 상행/하행"만으로는 부족**하다.

최소한 아래 중 일부는 반드시 필요하다.

- `branch_key`
- `service_pattern`
- `destination_station_id`
- `display_direction_label` (예: 내선순환, 외선순환, 인천행, 신창행)

# 4. DB 컬럼 제안

아래 정도가 있으면 1호선/2호선을 둘 다 무리 없이 표현하기 쉽다.

```md
lines
- id
- name
- color

stations
- id
- name
- code

line_stations
- id
- line_id
- station_id
- station_code
- branch_key          // main, seongsu_branch, sinjeong_branch, gyeongin, gyeongbu, gwangmyeong_shuttle 등
- order_index

service_patterns
- id
- line_id
- code                // 2_inner, 2_outer, 2_sinseoldong, 2_kkachisan, 1_incheon, 1_shinchang ...
- display_name        // 내선순환, 외선순환, 신설동행, 까치산행, 인천행, 신창행 ...
- direction_type      // inner, outer, northbound, southbound, branch_shuttle 등
- destination_station_id

service_pattern_stations
- id
- service_pattern_id
- station_id
- stop_order
```

핵심은,
**물리 노선(line) / 노선 위 역 순서(line_stations) / 실제 승객이 타는 운행계통(service_patterns)**
을 분리하는 것이다.

# 5. 최종 요약

## 2호선 요약

- 본선은 **상행/하행보다 내선/외선**으로 봐야 한다.
- **순환선**이라 방향 정의 방식이 일반 노선과 다르다.
- **성수지선(신설동행)**, **신정지선(까치산행)** 이 따로 있다.
- 따라서 `branch + service_pattern + destination`이 중요하다.

## 1호선 요약

- 겉보기에는 직선형이지만 실제로는 **공통구간 뒤 다중 분기 노선**이다.
- **구로 이후** 경인선 계통과 경부선 계통의 분기가 핵심이다.
- 실제 이용 안내는 `상행/하행`보다 **인천행 / 신창행 / 서동탄행 / 광명행** 같은 종착 기반이 중요하다.
- 따라서 1호선도 `direction`만으로는 부족하고, `branch + destination + service_pattern`이 필요하다.

# 6. 출처 메모

- 서울교통공사 실시간 열차 운행 정보: 2호선 열차가 **내선순환 / 외선순환 / 신설동행 / 까치산행** 형태로 실제 표기됨.
- 서울교통공사·공공데이터포털 수도권 지하철 노선도/노선별 역 정보: 2호선 본선·지선 구조 및 최신 노선도 기준 확인.
- 코레일 간편지연증명서 및 전철 시간표 안내: 1호선이 **소요산방면 / 인천방면 / 신창방면** 등 방면 기준으로 운영 안내됨을 확인.
- 코레일/전철 시간표 검색 결과: 1호선 실제 열차 종착 패턴에 **광명행 / 서동탄행 / 천안행 / 인천행 / 신창행** 등이 사용됨.
